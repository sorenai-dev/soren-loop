# Threat Model 06: Security Requirements, Tests, and Spike Consequences

Priority: **MUST-MVP** blocks the Phase 1 smoke test from counting as done. **SHOULD-MVP**
means "ship in Phase 1 unless cut explicitly, with the risk accepted in writing." **LATER**
means "required before the named phase or feature ships."

---

## 1. Requirements for the RFC (priority order)

### MUST-MVP

| ID | Requirement | Threats addressed |
|----|-------------|-------------------|
| SR-01 | **Headless agent invocation hardening.** The CLI runs `claude -p` with `--setting-sources user` (no project `.claude/settings*.json`, no `.mcp.json`) and `--settings '{"disableAllHooks": true}'`. It loads our plugin explicitly from the CLI's own pinned copy, with the hash verified. It explicitly denies `WebFetch` and `WebSearch`, and uses `--permission-prompts none`. A container-local user settings file is written by the CLI per run. Repo `CLAUDE.md` still loads (verify in S6). | T8.1, T8.5, T8.8, T9.1 |
| SR-02 | **Two-phase sealed sandbox** for both `plan` and `build`, with a **fresh container per phase and per check run**. Phase A (hydrate) runs **only on a pristine export of `base_sha` from the trusted gitdir**, never on an agent-touched tree (resume and rework included), with lifecycle scripts disabled where the ecosystem allows and network limited to registries. Its output is a **read-only dependency layer**. Phase B (agent) has egress to Anthropic endpoints only (take the list from the reference firewall script) and DNS restricted to the same. The exhaustive mount list for phase B is: the run tree (rw for build, ro for plan); the dependency layer (ro); the plugin (ro); a per-run ephemeral config dir; and the Claude credential, **copied into the per-run config dir** (RFC `15` §2) or passed as `CLAUDE_CODE_OAUTH_TOKEN`; the persistent credential volume is never mounted in phase B (S5 verifies refresh behaviour, **UNVERIFIED**). The dependency cache volume is mounted in phase A only. Phase B sees only the read-only layer that phase A produced, never dependencies inside the agent-writable tree, so a tampered test runner can't fake the fresh-container checks. There is no Docker socket. The agent runs non-root and cannot change firewall rules. No host env passes except the Claude auth variable. There is no SSH agent or git credential helper, and `.env*` files are excluded from the export. **Deterministic checks re-run in a new phase-B container** over the tree (ro) and the pristine dependency layer, never inside the agent's container. | T8.2 to T8.4, T8.16, T9.2, LLM02, LLM06 |
| SR-03 | **`plan` is least-privilege.** It runs in the SR-02 sandbox with read-only tools (Read, Grep, Glob), **never Bash** (decision 22), and no Write outside the spec output file. | `03` §1 form-mode note |
| SR-04 | **Deterministic `submit` policy** (outside the sandbox, no LLM). (a) Path deny-list: `.github/**`, `.claude/**`, `.mcp.json`, `CLAUDE.md`, `AGENTS.md`, `.devcontainer/**`, `CODEOWNERS`, `.gitattributes`, `.gitmodules`, `.npmrc`, `.yarnrc*`, `.husky/**`, `.git` (any path component, matched case-insensitively after Unicode normalization), `.gitignore` (RFC CLI-H2), hook-manager configs (`lefthook*.yml`, `.pre-commit-config.yaml`), `.vscode/**`, `.idea/**`, `.envrc`, Dockerfiles, CI and build config. (b) Owner-configured allow globs, **default deny** when none are configured. (c) Manifest and lockfile changes are blocked (no new dependencies in V1, decision 16). (d) Flag gating, defined deterministically (Zod M8): the owner's test command passes with the OpenFeature in-memory provider forcing the request's `sl_…` key to `false`, and at least one test file references the key. The owner's test-setup file that installs the `InMemoryProvider` from `SL_FLAG_FIXTURE` (Zod D6) is registered in site config (step-up) and **hard-blocked** for agent edits. The checks verify that its blob hash equals the base commit's, so the agent can't make the flag-off gate pass vacuously. No `@sorenai` SDK honours `SL_FLAG_FIXTURE`. Paths the spec intends to touch are a structured `paths[]` field in the spec envelope, hashed in `H_spec`, and checked against the path policy at G2 and at `submit`. (e) Secret scan of the diff, commit messages, and PR body. (f) No binaries; diff size cap. Per decision 15: **hard blocks** (no override) for deny-listed paths including `.github/**` and workflows, and for detected secrets. **Step-up override** only for out-of-eligibility paths under (b); overrides are logged and labelled on the PR. | T9.1, T9.2, T10.2, T11.5, AB3, AB8 |
| SR-05 | **Content-bound approvals.** The WebAuthn challenge is `H(action‖request_id‖content_hash‖nonce)`, single-use, valid 2 minutes, `userVerification: required`. G1 binds `H_req`; G2 binds `H_spec` and records `H_req` as its parent. Hashes are taken over normalized text (invisible characters stripped). The CLI refuses `plan` or `build` on any mismatch and fetches specs only from the backend, never from the issue. | T5.3, T10.8, `03` §5 |
| SR-06 | **Untrusted-text handling in the dashboard and email.** Strict nonce-based CSP with no `unsafe-inline` or `unsafe-eval`; Trusted Types; markdown rendering without raw HTML; invisible, bidi, and confusable characters detected and shown; per-field length caps; requester content visually fenced. Email: fixed subject, plain text, attacker text truncated and defanged, one dashboard link. | T5.1, T6.1, AB7, AB9 |
| SR-07 | **Widget identity.** `jose` verify with an explicit algorithm allowlist, `iss`→site, `aud`, `exp` ≤ 5 minutes, `jti` replay cache. JWKS fetched under the three-layer SSRF defense. Session token bound to `(site_id, sub)`, kept only in iframe memory. Strict `postMessage` origin checks, then a `MessageChannel`. `frame-ancestors` per site. JWT schema `sl.widget_jwt.v1` (Postel M5): header `alg ∈ {ES256, EdDSA}`, `kid` required, and `typ: "sl-widget+jwt"` required (RFC 8725 explicit typing, so another host JWT signed by the same key is never accepted). `aud` = **this install's exact API origin**, so a token minted for one install is useless at another (for example, staging versus prod). Leeway is **30 s** on `exp`, `iat` and `nbf`; `iat` may not be later than now plus the leeway; `exp − iat ≤ 300`; the `jti` cache TTL is `exp` plus the leeway. `email` and `email_verified` are honoured only when the site has opted in (SR-39c). Docs recommend a dedicated signing key for soren-loop. The widget sees only a generic `401`; the specific reason is visible to the owner only. `POST /v1/owner/sites/{id}/widget-token/check` (Postel D-M4) requires an owner session, `Sec-Fetch-Site: same-origin`, and a rate limit. It never consumes a `jti` or creates a session, rejects tokens for other sites, and logs only a token hash. Rated **L/L**: the oracle reaches only someone who already holds the owner session. **Widget served from a separate host from the dashboard and owner API.** `__Host-` cookies. | T1.x, T2.x |
| SR-08 | **GitHub** (decisions 24, 25). Fork model confirmed by S1. **Two Apps.** The *PR App* is installed upstream with exactly `pull_requests: write`, `issues: write`, `deployments: read`, `contents: read`, and `metadata: read`; never any `contents` permission above read (decision 26; the start-up check and `doctor` fail on it). The *push App* is installed **only** on the bot-only fork with `contents: write` and `metadata: read`. Never `Workflows`. Installation tokens are minted per operation, down-scoped to one repo, never inside the sandbox; any non-201 mint is a hard error (S1 F3). PRs are created with `maintainer_can_modify: false`. The two private keys are separate and separately rotatable. A backend start-up check and `doctor` verify each App's granted permissions and installation repos, and fail on extras. `doctor` fails if the fork has human pushers. Webhook HMAC is verified in constant time with `X-GitHub-Delivery` dedup. Ancestry check before `deployed`. `doctor` blocks or warns on `pull_request_target`/`workflow_run` workflows that check out PR heads. Rework feedback only from owner-authored input. GitHub reviews become *pending* feedback, and rework needs a step-up `rework.approve` over `sl:rework:v1(h_spec, h_fb)`, a receipt the CLI verifies (RFC B5, T23). The rework tree is exported from the trusted gitdir at the **recorded** `head_sha` (SR-41), never from a blindly fetched fork head. Rework pushes are fast-forward only. `--fresh` opens a new PR and closes the old one, revoking its tokens. | T10.x |
| SR-09 | **CLI auth and credential issuance.** Device flow whose approval page requires step-up and shows client context. Short-lived access tokens with rotating refresh in the OS keychain; reuse of a rotated refresh token revokes the family. Tokens are listed and revocable in the dashboard, and never logged or passed in argv. **Credential-issuing endpoints are exempt from response caching** (Postel B2): `/widget/sessions`, the device-flow token routes, refresh, and `push-token` never store a credential in `idempotency_keys` or anywhere else; the idempotency store holds no secret for any route. Push token: minting is allowed only in `building{ready}` with an approved `H_spec`, a pre-check record (SR-26h), and a server-checked path policy. The server stores `{token_id, minted_at, expires_at}` plus the token envelope-encrypted (SR-14) **only until expiry and only for revocation**, never returned by any route. A repeat call returns `409 push_token_already_minted` with no token. `{replace: true}` revokes the prior token at GitHub, then mints; it is audited and **capped at 2 per run**. The CLI revokes its token immediately after a successful push, and the server revokes any unrevoked token when the request leaves `building`. Upstream fetch credential (T24): **default to the owner's existing git credential**, invoked only for `git fetch` of the exact upstream URL into the trusted gitdir, so the server mints no repo-read capability. Fallback (CI, or no owner credential): a server-minted PR App `contents: read` token, 1 h, one per run, minted only with a live lease or in `owner_approved`/`plan_approved`, audited, and only for a **sender-constrained (DPoP-bound) CLI token**. | T7.1, T7.2, T7.5, T7.6, T10.14 |
| SR-10 | **Step-up on every high-impact owner action:** G1 and G2 approvals, rollout widening, `enableAll`, the self-serve mark, SR-04 overrides, adding or removing authenticators, CLI device approval, site key or JWKS changes, vendor credential changes. No email-only account recovery. | T5.5, T5.6, T11.4 |
| SR-11 | **Caps.** Per-`sub` open-request cap (default 3) and daily cap; per-site daily cap; field and size caps; owner "pause intake" and "block requester" actions; notification digests. | AB1, T6.2 |
| SR-12 | **Status feed.** Stage names only; 128-bit random request IDs; authorization by `(site_id, sub)`; no flag keys, repo names, or links. | T12.1, AB6 |
| SR-13 | **Flag plane.** Opaque `sl_<random>` keys with metadata server-side; the flagd sync endpoint is authenticated or network-restricted and never internet-reachable; the vendor token is scoped to its project and environment; `FlagWriter` refuses keys outside the `sl_` namespace; writes happen only through outbox effects of state-machine events, including the no-transition events in the table (RFC `03` row 43). `requester_opt_out` (withdraw after merge) removes only the caller's own session `sub` from targets; `retire` archives and never closes, so a live flag always stays killable. Documented rule: **flags are rollout controls, not authorization.** | T11.1 to T11.4 |
| SR-14 | **Secrets at rest.** Vendor credentials and the intake key are envelope-encrypted with a key held outside the DB; CLI and session tokens are stored as peppered HMAC; the App private key is file-mounted (`0400`) and never in the DB; no secret is ever logged. | T4.2, T10.7 |
| SR-15 | **Audit trail.** Append-only `request_transitions` with actor type, recording "CLI on behalf of owner for request R" distinctly from "owner"; every token mint, approval (with assertion ID), override, and flag write; key prefixes and hashes only. | T4.5, T5.7 |
| SR-16 | **Release integrity.** npm trusted publishing plus provenance for the CLI and SDKs; SHA-pinned actions in all workflows; protected release environment with a required reviewer; signed server image with SLSA provenance and an SBOM; package names reserved. | SC1, SC4, SC6 |
| SR-17 | **Issue projection.** Request ID plus an owner-edited title only; `@`, `#`, and links neutralized; PII scrubbed; specs never projected; **off by default for public repos**. | T10.10, AB4, AB6 |
| SR-18 | **Model output is advisory.** The tdd-pair outcome JSON and any model-written text are schema-validated and **never** gate a transition alone. State changes come from deterministic checks or owner actions. | T8.7, LLM05 |
| SR-26 | **Block-only security pre-check** (decision 23 with ratified amendments A23-1 to A23-8; design and threats in `03` §7). It runs at five points: L3 server-side at submission in every mode (A23-1); L1 and L3 at intake in API-key mode; all layers at step 0 of `plan`; all layers on the generated spec before G2 (A23-2); and at `build` start, where the CLI verifies the record against `H_spec` and re-runs L2 against the actual base (A23-2). (a) L1: a no-tool `claude -p` classifier (Zod M12). It runs on the host **only** with a fresh `CLAUDE_CONFIG_DIR` holding just a copied credential, an empty strict MCP config, no plugins, an empty temp cwd, input on stdin, and the SR-01 flags, **and only once S6 shows the init event lists zero tools and zero MCP servers** (ST-35). Otherwise it runs inside a sealed phase-B container. The server-side PC-I calls the API directly, with no Claude Code involved; untrusted text is fenced as data; output must match a strict verdict schema (one JSON object; `clean`/`flagged`; category enum; spans capped and verified as offsets into the normalized input). (b) L2: deterministic diff of `CLAUDE.md`, `AGENTS.md`, `.claude/**`, and `.mcp.json` since the owner-trusted commit. That pointer is set only by the owner with step-up, never auto-advanced, and must be an ancestor of the base, or the request holds. (c) L3: deterministic rules for invisible, bidi, and confusable characters; encoded payloads; URLs; shell-like strings. (d) Any L1, L2, or L3 hit, any schema failure, and any error, timeout, or refusal → `security_hold`. Errors carry the reason `precheck_unavailable` with a Retry action. (e) A hold is cleared only by the owner with step-up whose challenge binds `sl:hold_clear:v1(request_id, verdict_id, content_hash, l2_fingerprint)` (RFC `04` §3, adopted everywhere, Zod M15). It is recorded as a `clearances` row; content or L2 changes re-run the pre-check. (f) `clean` has **no** gating or UI-assurance effect (`03` §7.2). (g) The requester-facing stage for `security_hold` matches the surrounding normal state. (h) The server requires a pre-check record for the current hash and base before accepting a plan upload, starting `build`, or minting a push token. (i) A per-requester flag-rate throttle that counts **only `flagged` verdicts with at least one verified span inside requester-supplied fields** (L1 or L3), derived from `prechecks` rows over a rolling 24 h. L2 hits, `precheck_unavailable`, and holds the owner cleared never count (Zod M3); bulk reject is allowed, bulk clear is not (A23-8). Spans render only as highlights of the original input, under SR-06. | T3.1, T9.1, PC1–PC9, AB3 |
| SR-27 | **PII retention** (decision 19, Zod M7): requester text, display name, `sub`, and `requesters.email_enc` are deleted 90 days after a request closes, or on request. A tombstone keeps IDs, hashes, and transitions for audit. The purge also covers: `outbox.payload` (flag effects carry `sub`s); `idempotency_keys.response` (24 h maximum, and request text is redacted from it); `runs.advisory`; `sub`s in the flagd document and its history; and CLI run directories, via a CLI `gc` on every `pull` keyed to server tombstones. Text on GitHub (PR, commits, issue) carries only `public_ref` and the owner-edited title; it is outside our purge, which the docs state. | AB4, LLM02 |
| SR-28 | **Host-side git and tree hygiene** (RFC CLI-H1, broadened). (a) No gitdir of the owner's repo (per-worktree or common) is mounted into the sandbox; the agent gets a plain tree or a sandbox-internal clone. (b) Every host git command in `submit` and `inspect` runs with a CLI-owned `--git-dir` and `--work-tree`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` set to a CLI-owned minimal file (owner identity and opt-in signing settings only), `GIT_TERMINAL_PROMPT=0`, no pager, plus `-c core.hooksPath=/dev/null -c core.fsmonitor=false -c protocol.file.allow=never -c protocol.ext.allow=never`. (c) Push goes to an explicit fork HTTPS URL with an ephemeral credential; remote config, `insteadOf`, and proxies are never consulted. Fetching a private upstream into the trusted gitdir uses a **server-minted, read-only, per-run fetch token** (PR App `contents: read`, 1 h, delivered by `GIT_ASKPASS`, audited, never inside the sandbox) (Zod M13). (d) The tree is walked with lstat only (no symlink following); new symlinks, gitlinks, FIFOs, devices, and `.git`-equivalent path components are hard-blocked. (e) The tree lives in a CLI-owned run directory with no `.git` entry. The pre-run `.git` hash (if any) is verified after the run, and any change hard-fails and quarantines the tree. File selection uses the base commit's ignore rules. | T8.9 to T8.15 |
| SR-29 | **WebAuthn and origin scoping** (RFC SU-1, broadened). The RP ID is the exact dashboard host. The widget host is neither equal to nor a subdomain of the RP ID, and is never listed in related origins. Assertions are verified against the exact dashboard origin (`expectedOrigin`). State-changing routes require `Sec-Fetch-Site: same-origin`, an exact `Origin` match, and a CSRF token. Only `__Host-` cookies are read. `doctor` checks the host relationship. | T5.8, T1.4 |
| SR-35 | **One step-up authorizes one action** (RFC SU-2, decision 28). Every step-up challenge is derived from `H(action‖target_id(s)‖content_hash‖nonce)` (the SR-05 construction, applied to every SR-10 action), is consumed by the first state change it authorizes, and creates **no elevated-session window**. A batch (bulk reject only, A23-8) is one action over an explicitly enumerated ID set that is hashed into the challenge. | T5.1, T5.5, T5.8 |
| SR-36 | **Browser flag evaluation goes only through the host OFREP handler** (RFC FL-1, decision 28; amended for Postel M6). `@sorenai/loop-node` ships `createOfrepHandler({flagdUrl, allowlist, getUser})`. It accepts single-flag **and** bulk evaluation (the stock OFREP web provider evaluates in bulk; **UNVERIFIED**, S4), strips the browser's context, injects `targetingKey` from the host session via the same `SorenLoopUser` type `createWidgetToken` takes, **filters every response to the allowlist**, and drops metadata and reasons. The allowlist is the set of `sl_…` keys referenced by the shipped client bundle, never "all `sl_` keys". Enumeration is closed by the allowlist plus the injected context, not by the path. flagd's evaluation and sync ports bind to a private interface by default. | T11.2, AB6, T2.5 |
| SR-37 | **Hash-chained audit tables** (RFC AU-1, decision 28; scope fixed per Zod M6). Chained tables (RFC `04` §4): `request_transitions`, `approvals`, `clearances`, `trusted_commits`, `notification_policies`, and `audit_events`. Every other SR-37 category (token mints and revocations, policy overrides, flag writes, owner-contact and SMTP changes) **must** be written as an `audit_events` row in the same transaction as the change. There is one chain per `(site_id, table)`, appended under `pg_advisory_xact_lock(chain_id)`. Columns: `chain_id`, `seq`, `prev_hash`, `row_hash = SHA-256("sl:audit:v1"‖prev_hash‖JCS(row))`. The application's DB role has INSERT only (no UPDATE or DELETE). **Export the chain heads** to a witness the DB writer cannot reach or rewrite: append-only object storage with object lock, or a separate host, **after every step-up action**; the owner's inbox nightly; and the CLI on every `pull`. A verifier recomputes the chains against the witnesses, and a mismatch raises the locked `owner.audit_chain_mismatch`. The chain detects rewrites, deletions, and truncation of history; it does not prove that new rows are authentic (SR-19 does that for approvals). | T4.3, T4.5, T5.7 |
| SR-38 | **Interactive builds are hardened identically** (decision 27). `build --interactive` uses the same sealed sandbox (SR-02), SR-01 flags, SR-28 run tree, PC-C check, and SR-04 `submit` policy as headless builds. Only the auditor changes. Owner approvals inside the Claude Code UI cannot widen egress, mounts, or settings, because those are set by the CLI outside the session. Interactive mode attaches agent output to the owner's TTY, so terminal escape sequences (OSC 52 clipboard write, OSC 8 links, title changes) are a host channel. Whether Claude Code's TUI strips them is **UNVERIFIED**; the CLI relays the TTY through a filter that passes **SGR only** and strips OSC, DCS, APC, PM, and all other CSI. Non-SGR CSI covers terminal queries whose replies inject keystrokes, and cursor movement that can hide text. A bare `\r` that would overwrite a line is rendered as a visible line break (Zod m6). | T8.x, decision 27 |
| SR-19 | **Approval receipts, verified by the CLI. MUST-MVP with no escape hatch.** At `login`, the CLI pins the owner's WebAuthn credential public keys. A key is added to the pin set only through a receipt signed by an already-pinned key over `authenticator_added` (step-up). Before `plan` or `build`, the CLI verifies the stored G1 and G2 assertions over the SR-05 challenge: origin, `rpIdHash`, the UV flag, a pinned key, and the challenge recomputed from local content. **Whenever a local pre-check flags but the server reports the hold as already cleared, the CLI verifies the `clear_hold` receipt** for the exact clearance binding (SR-26e) and refuses on failure (Zod M9: otherwise a compromised server launders holds). | T7.3, T4.3 |
| SR-39 | **Notification policy cannot reveal a hold, and locked alerts cannot be silenced** (decision 30, RFC `14`). (a) Requester events are created only when the requester stage changes. The type carries `stage`, `request_id`, and `stage_since_hour` only. Override keys are limited to the seven stages, under a strict schema. (b) Requester deliveries on every channel, including the Phase 2 webhook relay, are scheduled at `ceil_hour`. Requester templates are identical across every `closed{*}` cause and contain no reason, verdict, or requester-supplied title. (c) Requester email comes only from a host-JWT `email` claim with `email_verified: true`, on site opt-in. It is envelope-encrypted, never logged, purged under SR-27, and sent with `List-Unsubscribe` and a per-recipient rate limit. (d) Suppressed rows and all notification metrics are owner- or operator-only: `/metrics` on the internal listener, no `request_id` or `sub` labels, and per-tenant isolation in hosted mode. (e) Locked owner kinds are `security_hold_entered`, `precheck_unavailable`, `app_permission_check_failed`, `outbox_dead`, `audit_chain_mismatch`, `authenticator_changed`, `cli_device_approved`, `owner_contact_changed`, and `policy_changed`. They are `defaults ∪ add_channels` only. `dashboard_inbox` is never coalesced. Email coalescing is per `(site, kind)`, leading-edge, 15-minute window, lists every `request_id` grouped by requester, and marks each row `sent_coalesced` with the message ID. (f) Changing the owner's address or the SMTP config requires step-up and notifies the old address. An undeliverable locked channel raises a persistent dashboard banner and a `doctor` failure. `outbox_dead` for a `notify.*` row routes to `dashboard_inbox` only, so it cannot loop. (g) A policy `PUT` or `DELETE` requires one step-up whose challenge binds the action, `site_id`, the base policy version, and `H("sl:notification_policy:v1"‖JCS(override))`. A stale base version returns 409. The dashboard renders the effective-policy diff being signed. Version rows and audit events sit in the SR-37 chain. | AB6, AB7, A23-5, T6.5, T6.6, T12.4 |
| SR-40 | **No hold disclosure outside notifications.** (a) GitHub artifacts carry an opaque `public_ref` that cannot be linked to the widget `request_id`. PR bodies, labels, commit messages, and issues never mention pre-check verdicts, holds, or clearances; those stay in the dashboard. (b) The A23-8 pause is indistinguishable from normal operation. Recommended: shadow-accept, where submissions are stored and shown as `received` within a per-`sub` hard daily cap, are grouped as throttled for the owner, and send no owner notification beyond the single pause notice. That beats returning `limit_reached` to a requester who has no open requests. Every widget `limit_reached` (cap, paused site, intake LLM budget) carries the same body, the same headers, and `retry_after_seconds: null` (Postel m5). | A23-5, PC6, T12.5 |
| SR-41 | **The fork branch is immutable after `submit`** (new, from Postel B2). The server records `head_sha` when it opens the PR. A `pull_request.synchronize` on a bot PR, or any fork-branch head that differs from the recorded `head_sha` without a server-issued rework push, moves the request to `stalled{reason: head_tampered}`, labels the PR as do-not-merge, and raises the locked `owner.pr_head_changed`. The PR-open guard is "the compare API's fork branch head == `head_sha`", since the server cannot observe "the token was used" (Zod minor 4). The only exemption is our own push. `runs.expected_head`, declared at mint (row 22), is honoured only while that run is in `building{ready, submitting}`. It is consumed when row 23 pins the head, after the server's SR-04 re-check of the cumulative diff; a `replace` mint overwrites it. Any later `synchronize` is tampering. A merge of a superseded PR raises the same locked `owner.pr_head_changed` with `reason: superseded_pr_merged`, and the merge head must equal the active PR's pin (row 25). | T10.14 |
